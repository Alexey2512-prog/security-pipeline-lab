# Этап 2. Экскурсия по pipeline

Workflow находится в `.github/workflows/security-pipeline.yml`. **Workflow** —
описанный в YAML автоматический процесс GitHub Actions. Он состоит из пяти
независимых **jobs — заданий**.

## 1. Functional tests

Устанавливает приложение и запускает `pytest`. Ожидаемый результат — успех.

Это контрольная группа эксперимента: мы доказываем, что уязвимости не обязательно
проявляются как функциональные ошибки.

## 2. SAST with Semgrep

Semgrep читает Python-код и сопоставляет его с правилами из
`security/semgrep.yml`. Ожидаемый результат первого запуска — ошибка задания.

Флаг `--error` превращает найденные нарушения в ненулевой **exit code — код
завершения**. По соглашению код `0` означает успех, другой код — ошибку. GitHub
Actions использует его как security gate.

## 3. SCA with pip-audit

Проверяется отдельный файл `lab/vulnerable-requirements.txt`. Он содержит старую
версию `urllib3`, которая не входит в рабочее приложение. Ожидаемый результат —
ошибка и перечень идентификаторов уязвимостей.

При локальной проверке 19 июля 2026 года SCA также обнаружил новую уязвимость в
Flask 3.1.2. Рабочая версия была сразу обновлена до 3.1.3, после чего аудит
`requirements.txt` прошёл. Это иллюстрирует непрерывность процесса: безопасность
зависимости меняется при публикации новых сведений, даже если код не менялся.

## 4. Container scan with Trivy

Docker собирает итоговый образ, после чего Trivy проверяет:

- **OS packages** — пакеты базовой операционной системы;
- **library packages** — библиотеки языка программирования.

Pipeline блокируется только при `HIGH` или `CRITICAL` с исправлением. Это первый
пример **risk threshold — порога риска**. Порог нужен, потому что блокировать
выпуск на любой информационной находке обычно непрактично.

## 5. DAST with OWASP ZAP

Приложение и сканер запускаются в отдельной Docker-сети `security-lab`. ZAP
выполняет **active scan — активное сканирование**, то есть отправляет потенциально
опасные тестовые данные.

Активный скан разрешён только для систем, которыми вы владеете и которые явно
предназначены для тестирования. Нельзя менять target на чужой или production URL.

Отчёты сохраняются как **artifact — артефакт запуска**, файл, который можно
скачать со страницы завершённого workflow:

- `zap-report.html` — отчёт для человека;
- `zap-report.json` — структурированные данные для дальнейшей автоматизации.

## Почему задания независимы

Независимые jobs запускаются параллельно и дают отдельные сигналы. Если SAST
нашёл проблему, это не мешает получить отчёт SCA или DAST. В производственном
pipeline после исследовательской фазы можно добавить итоговое задание, которое
собирает решения всех gates и разрешает или запрещает deployment.

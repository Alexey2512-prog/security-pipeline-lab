# Security Pipeline as Code — учебная лаборатория

Этот проект показывает, как проверки безопасности становятся частью CI/CD,
то есть выполняются автоматически при каждом изменении кода.

> Внимание: приложение намеренно уязвимо. Запускайте его только локально или в
> изолированной CI-среде. Не публикуйте контейнер в интернете и не используйте
> код из помеченных `LAB-VULNERABILITY` участков в реальных приложениях.

## Что мы исследуем

Обычные функциональные тесты и проверки безопасности отвечают на разные
вопросы:

| Проверка | Главный вопрос |
| --- | --- |
| Unit/integration tests | Делает ли программа то, что от неё ожидают? |
| SAST | Есть ли опасные конструкции в исходном коде? |
| SCA | Есть ли известные уязвимости в зависимостях? |
| Container scan | Есть ли уязвимости в ОС и пакетах Docker-образа? |
| DAST | Можно ли атаковать уже запущенное приложение извне? |

Учебный эффект: тесты должны пройти, а SAST, SCA и DAST — обнаружить
подготовленные проблемы. Красный pipeline на первом этапе является ожидаемым
результатом эксперимента, а не поломкой проекта.

## Словарь

- **CI — Continuous Integration, непрерывная интеграция.** Код автоматически
  собирается и проверяется после push или pull request.
- **CD — Continuous Delivery/Deployment, непрерывная доставка/развёртывание.**
  Прошедшая проверки версия подготавливается или автоматически отправляется в
  среду выполнения. В этой лаборатории реального deployment пока нет.
- **Pipeline — конвейер.** Последовательность автоматических задач: тестирование,
  анализ, сборка и проверка артефактов.
- **SAST — Static Application Security Testing.** Анализ исходного кода без
  запуска приложения. Здесь используется Semgrep.
- **SCA — Software Composition Analysis.** Анализ сторонних компонентов и их
  известных уязвимостей. Здесь используется pip-audit.
- **DAST — Dynamic Application Security Testing.** Проверка работающего
  приложения снаружи, обычно через HTTP-запросы. Здесь используется OWASP ZAP.
- **OWASP — Open Worldwide Application Security Project.** Сообщество и фонд,
  создающие открытые материалы и инструменты по безопасности приложений.
- **CVE — Common Vulnerabilities and Exposures.** Общепринятый идентификатор
  публично известной уязвимости.
- **Docker image — образ контейнера.** Неизменяемый шаблон с приложением,
  интерпретатором, библиотеками и частью операционной системы.
- **Security gate — контрольный барьер.** Правило, которое останавливает pipeline,
  когда риск выше допустимого порога.
- **False positive — ложноположительное срабатывание.** Инструмент сообщает об
  уязвимости, которой в реальном контексте нет.
- **SQL injection — внедрение SQL.** Ввод пользователя превращается в часть
  команды базе данных.
- **XSS — Cross-Site Scripting, межсайтовый скриптинг.** Ввод пользователя
  возвращается как исполняемый браузером HTML или JavaScript.

## Структура проекта

```text
app/                         учебное Flask-приложение
tests/                       функциональные тесты
security/semgrep.yml         собственные правила SAST
lab/vulnerable-requirements.txt  фикстура для урока SCA
.github/workflows/           pipeline GitHub Actions
Dockerfile                   инструкция сборки контейнера
docs/                        пошаговые учебные материалы
```

## Этап 1: локальный запуск без Docker

Требуется Python 3.13 или совместимая версия 3.10+.

```powershell
python -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install --requirement requirements-dev.txt
python -m pytest
python -m app.main
```

После запуска откройте `http://127.0.0.1:8080/health`.

## Этап 2: запуск через Docker

```powershell
docker build --tag security-pipeline-lab:local .
docker run --rm --publish 127.0.0.1:8080:8080 security-pipeline-lab:local
```

Публикация порта привязана к `127.0.0.1`, поэтому сервис доступен только на
вашем компьютере.

## Этап 3: наблюдение за pipeline

1. Создайте пустой репозиторий на GitHub.
2. Добавьте этот проект и отправьте ветку `main`.
3. Откройте вкладку **Actions**.
4. Сначала изучите зелёную задачу `Functional tests`.
5. Затем по очереди разберите вывод SAST, SCA, container scan и DAST.

Не исправляйте все уязвимости сразу. Ценность лаборатории — увидеть сигнал
каждого инструмента отдельно, сформулировать причину и только затем внести
исправление.

## План следующих учебных итераций

1. Запустить pipeline и сохранить исходные отчёты.
2. Исправить SQL injection параметризованным запросом.
3. Исправить XSS автоматическим экранированием шаблона.
4. Обновить уязвимую зависимость и сравнить отчёт SCA.
5. Настроить baseline: старые находки видны, но блокируются только новые.
6. Добавить SARIF и сводный отчёт рисков.
7. Измерить время сканирования и количество ложных срабатываний.
